# Phase 3: Bounded Sync Requests - Context

**Gathered:** 2026-08-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Bound the work generated by authorized reserve `META_REQ` and `DATA_REQ` messages and loot-distribution `SNAP_REQ` messages. Requests that exceed the per-sender limit must be rejected before reserve payload construction, snapshot construction, response serialization, chunk creation, or transport queue allocation.

This phase preserves the current RMA prefixes, protocol-version-5 envelopes, payload shapes, request/response correlation, authorization behavior, and normal first-request behavior. It does not change outbound client request throttling, raid-history synchronization, ChatThrottleLib, user-facing synchronization workflows, wire error formats, or SavedVariables.

</domain>

<decisions>
## Implementation Decisions

### Request budgets
- Rate-limit each normalized sender and request kind independently. `META_REQ`, `DATA_REQ`, and distribution `SNAP_REQ` do not share a counter.
- Reserve and loot-distribution admission state remain independent. Activity in one service must not reduce the budget of the other.
- This separation is required so the normal reserve flow can send `META_REQ` and then `DATA_REQ` immediately without self-throttling.
- Only structurally valid and currently authorized requests consume a budget entry. Malformed, mistargeted, invalid-version, non-member, or otherwise unauthorized messages are rejected before rate admission.
- A valid authorized request consumes its budget even if the responder has no usable data and follows the existing no-data/failure behavior. Response work, including an existing error response, must still be bounded.

### Exact limit and expiry
- Admit one request per normalized sender and request kind every 5 seconds.
- Rejected attempts do not extend or restart the cooldown. Expiry is measured from the last admitted request.
- The exact boundary is inclusive: a request is eligible when elapsed time is greater than or equal to 5 seconds.
- Prune expired admission state lazily when relevant messages arrive. Do not add a timer, ticker, or `OnUpdate` solely for cleanup.
- Keep the number of tracked sender entries globally bounded within each owning service. After pruning expired entries, reject a previously unseen sender if capacity is still full; do not evict an active entry to admit it.

### Sender identity
- Use a case-insensitive canonical short-name identity for the budget. `Massimo`, `massimo`, and equivalent `Name-Realm` forms share the same entry.
- Reuse the established sender normalization semantics rather than creating an alternate identity rule for rate limiting.
- If sender normalization does not produce a valid non-empty identity, reject the request fail-closed and do not place it into a shared anonymous bucket.
- Re-evaluate group membership and feature authorization from the original sender on every request.
- A role change or group leave/re-entry does not clear a still-active cooldown. Once the sender becomes authorized again, the existing entry expires normally.

### Rejection and visibility
- A rate-limited request produces no addon response: no ACK, error envelope, snapshot, chunk, or queued message.
- Do not show ordinary chat output, warnings, popups, or UI state for rate-limit rejection.
- When debug logging is enabled, record only the first rejection for that sender/request-kind cooldown. Further rejected attempts during the same cooldown remain silent.
- Debug detail may identify the owning service, request kind, and normalized sender; it must not include request bodies, reserve data, snapshot contents, or other transferred state.
- Admission state and debug-deduplication state are transient session memory only. Login or `/reload` resets them; no SavedVariable or persisted schema is added.

### Codex's Discretion
- The exact bounded capacity for tracked sender entries, provided tests prove the bound, lazy expiry, and fail-closed behavior at capacity.
- Internal helper names and whether each owner uses one table keyed by request kind or separate tables, provided ownership and the independent budgets above remain clear.
- The smallest repository-consistent debug diagnostic keys and wording.
- Handler return values for silently consumed rejections, provided the message remains handled and cannot fall through to another protocol owner.
- Test fixture organization and whether the existing bounded-rate algorithm is reused directly or reproduced locally with less coupling.

</decisions>

<specifics>
## Specific Ideas

- At time `t`, an authorized sender may trigger one reserve `META_REQ`, one reserve `DATA_REQ`, and one distribution `SNAP_REQ`; none blocks the other two.
- A second request of the same kind at `t + 4.999` is rejected without response work. The same kind at `t + 5.000` is admitted.
- Replaying the rejected request repeatedly does not move the next eligible time beyond `t + 5.000`.
- `Player`, `player`, and `Player-Realm` cannot obtain separate quotas for the same short-name identity.
- The first rate-limited rejection can be diagnosed locally in debug mode, but a request flood must not become a debug-log flood.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `Modules/Comms.lua`: `Comms.NormalizeSender()` already supplies the short-name normalization used by communication owners; rate keys should add consistent case folding after this canonical step.
- `Database/DBSyncSession.lua`: already demonstrates a Lua 5.1-compatible bounded timestamp map with normalization, lazy expiry, a maximum peer count, exact retry boundaries, and focused regression coverage. It is a useful established pattern, although Phase 3 does not extend raid-history sync scope.
- `Services/Reserves/Sync.lua`: already binds `GetTime`, decodes closed version-5 envelopes, validates targets and bodies, checks group/authority state, and owns reserve synchronization runtime state.
- `Services/Loot/DistributionSession.lua`: already binds `GetTime`, validates version-5 envelopes, normalizes wire names, checks group membership, and owns distribution snapshot runtime state.

### Established Patterns
- Reserve `Sync:HandleMessage()` currently validates and authorizes at lines 589-609, then calls `sendMetadata()` or `sendData()` at lines 611-624. `sendData()` builds the canonical transfer, serializes it, chunks it, and queues messages, so admission must occur before that call.
- Distribution `HandleMessage()` currently decodes and checks membership at lines 2091-2112, then calls `PublishSnapshot()` at lines 2165-2167. `PublishSnapshot()` constructs and encodes the snapshot beginning at line 2023, so admission must occur before that call.
- Both communication protocols use distinct prefixes (`RMAResSync` and `RMADist`) and protocol version 5. These values and envelope layouts are compatibility-sensitive and must remain unchanged.
- Existing request handlers already return the message as handled when validation or authorization fails, which supports silent fail-closed rejection.
- ChatThrottleLib bounds transmission bandwidth but does not prevent expensive response serialization or queue allocation; inbound admission must happen before those operations.

### Integration Points
- Add reserve request admission inside `Services/Reserves/Sync.lua` after envelope/target/body validation and membership authorization, immediately before `sendMetadata()` or `sendData()`.
- Add distribution request admission inside `Services/Loot/DistributionSession.lua` after `SNAP_REQ` validation and membership authorization, immediately before `PublishSnapshot()`.
- Extend `tests/lua/harness/50_reserves_messaging.lua`, especially the existing correlated/bounded request cases, for `META_REQ` and `DATA_REQ` limits and proof that rejected requests do no serialization or queue work.
- Extend `tests/lua/harness/10_loot_distribution.lua`, especially the existing snapshot request correlation/bound cases, for `SNAP_REQ` limits and proof that rejected requests do no snapshot or queue work.
- Preserve existing static wire-contract checks and add exact cases for first admission, same-kind rejection, cross-kind independence, `t + 5` expiry, rejected-attempt non-extension, normalized aliases, map capacity, and debug deduplication.

</code_context>
